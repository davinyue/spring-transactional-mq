# 消费端自定义退避重试

## 背景

当前组件的消费失败处理没有可由消费者自定义的退避重试能力：

- RabbitMQ 消费失败后会占用当前消费线程等待 10 秒，然后通过 `basicNack(..., requeue=true)` 将原消息重新入队。
- Kafka 业务消费失败时会尝试将新事务消息立即投递到 topic 末尾；重投失败时才通过 `nack(10s)` 延迟重试。
- 两种 MQ 的消费失败语义不一致，也都无法表达“第几次重试”和“下次应在何时执行”。

需要增加消费端自定义退避重试。“首次失败后 2 分钟，后续依次为 4 分钟、8 分钟、16 分钟、32 分钟、1 小时、2 小时和 4 小时”作为一种可用策略示例，不是框架强制的次数或间隔。

## 目标

- 为 RabbitMQ 和 Kafka 提供语义一致的消费失败自定义退避能力。
- 消费失败后不阻塞消费线程，不阻塞 RabbitMQ 队列或 Kafka partition 的后续消息。
- 在业务事务回滚的同时，可靠记录下一次重试，避免消息丢失。
- 在 ACK 或 offset 提交结果不确定时，仍能依靠原始消息 ID 和数据库唯一约束防止重试任务逐轮放大。
- 框架不设置统一最大重试次数，是否继续重试及下次间隔完全由当前消费者的重试策略决定。

## 范围

- 由每个 `TransactionalMessageConsumer` 实现类声明自身的消费重试策略，不使用全局时间表。
- 增加消费重试次数、原始消息 ID、消费者编码和下次重试时间等框架内部元数据。
- 增加不阻塞消费线程的延迟重投机制。
- 调整 RabbitMQ 和 Kafka 消费监听器的失败处理、ACK/nack 顺序及重试上下文透传。
- 在消费者策略明确停止重试时保留相关失败审计信息。
- 增加与上述行为直接相关的单元测试、仓储测试和 MQ 监听器测试。
- 更新项目已支持的所有数据库建表脚本及存量表升级脚本。

## 非目标

- 本需求不调整生产端“数据库事务消息发送到 MQ 失败”的固定 60 秒重试策略。
- 不引入依赖 RabbitMQ 延迟消息插件的必选实现。
- 不使用长时间 `Thread.sleep` 或持有未 ACK 消息的方式实现退避。
- 不要求业务消费者自行计算重试次数或退避时间。
- 不由生产者按队列或 topic 维护消费端重试策略。
- 本次不调整正常消费成功时的业务事务和幂等语义。

## 关键设计

### 消费者级重试策略

在 API 层增加不可变的 `ConsumeRetryPolicy` 值对象。该对象统一封装“当前是否还能重试”和“下次需要等待多久”，RabbitMQ/Kafka 监听器不分别实现次数与间隔判断。

`ConsumeRetryPolicy` 至少提供以下预置策略：

1. 有限次固定间隔：显式指定最大重试次数，每次等待时间相同。
2. 有限次自定义间隔：按顺序指定每一次重试的等待时间，间隔数量即最大重试次数。
3. 无限次固定间隔：每次使用相同等待时间，框架不主动截止。
4. 不重试：消费失败后直接返回停止。

建议的创建方法：

```java
// 最多重试 5 次，每次间隔 1 分钟
ConsumeRetryPolicy.fixedDelay(5, Duration.ofMinutes(1));

// 自定义每轮间隔，间隔数量即总重试次数
ConsumeRetryPolicy.customDelays(
        Duration.ofMinutes(2),
        Duration.ofMinutes(4),
        Duration.ofMinutes(8),
        Duration.ofMinutes(16),
        Duration.ofMinutes(32),
        Duration.ofHours(1),
        Duration.ofHours(2),
        Duration.ofHours(4));

// 每分钟无限重试
ConsumeRetryPolicy.fixedDelayForever(Duration.ofMinutes(1));

// 不重试
ConsumeRetryPolicy.noRetry();
```

`ConsumeRetryPolicy` 对外提供统一判定方法：

```java
Optional<Duration> nextDelay(int retryCount);
```

判定语义：

- `retryCount = 0` 表示原始消息首次消费失败，此时查询第一次重试间隔。
- `retryCount = 1` 表示第一次重试消费失败，此时查询第二次重试间隔。
- 返回包含 `Duration` 的 `Optional` 表示继续重试，返回的时长即下次等待时间。
- 返回 `Optional.empty()` 表示当前策略已达最大重试次数或明确不重试。
- 自定义间隔策略使用 `retryCount` 作为间隔下标；当 `retryCount` 超出间隔数量时返回 `Optional.empty()`。
- 有限次固定间隔策略在 `retryCount < maxRetryCount` 时返回固定间隔，否则返回 `Optional.empty()`。
- 无限次固定间隔策略始终返回固定间隔。

例如，自定义间隔 `[2m, 4m, 8m]` 的判定结果为：

```text
nextDelay(0) = 2 分钟
nextDelay(1) = 4 分钟
nextDelay(2) = 8 分钟
nextDelay(3) = empty，停止重试
```

构造策略时即校验参数：有限固定间隔的重试次数必须大于零；所有继续重试的时长必须大于零；间隔无需递增且可以完全相同。

`TransactionalMessageConsumer` 增加 `ConsumeRetryPolicy getConsumeRetryPolicy()` 方法，具体消费者可返回上述任一策略。为保持接口兼容，默认实现返回 `ConsumeRetryPolicy.noRetry()`；业务需要重试时由消费者明确覆盖。

重试策略的归属是消费者实现，不是生产者、全局 starter 配置或框架维护的队列映射。消费者如需按环境调整策略，可在自身实现中注入业务系统配置后组装 `ConsumeRetryPolicy`。

### 推荐流程

```text
业务消费失败
        ↓
回滚业务事务及本次消费幂等记录
        ↓
在独立新事务中按 originalMessageId 和 retryCount 保存延迟重试记录
        ↓
重试记录保存成功后 ACK 当前消息
        ↓
后台派发线程在 nextDispatchTime 到期后重新投递
```

如果延迟重试记录保存失败，不得 ACK 当前消息，应回退到 MQ 原生的短延迟 nack/requeue，保证不因本地数据库故障丢失消息。

### 延迟调度方案

首选复用现有事务消息数据库派发能力：

- 为消费失败创建新的延迟派发记录，并将 `nextDispatchTime` 设为当前时间加本次退避时长。
- 复用已有的 `message_status + next_dispatch_time + id` 候选扫描和索引。
- 复用已有的多实例派发抢占令牌和租约机制。
- 不依赖 RabbitMQ 延迟插件，也不要求 Kafka 提供原生延迟消息。

存储方案确定为直接复用现有 `TXN_MESSAGE` 和 `TXN_MESSAGE_HISTORY`：

- 在事务消息主表和历史表增加 `originalMessageId`、`retryCount` 等消费重试元数据。
- 在事务消息主表上建立 `originalMessageId + retryCount` 唯一重试键，防止同一轮重试被重复创建。
- 延迟重试记录使用现有 `nextDispatchTime`、消息状态、派发抢占令牌和租约机制。
- 重试消息派发成功后沿用现有成功消息归档链路。
- 不新增专用消费重试表和独立重试调度器。

该方案必须同时实现 `originalMessageId` 与重试唯一键，不得仅新增 `retry_count` 字段。

### 消息 ID、原始消息 ID 与幂等

消息模型新增 `originalMessageId`，区分“当前投递尝试”和“原始业务消息”：

- `messageId` 使用事务消息派发记录的 `id`，标识当前具体投递尝试。
- 普通新消息首次发送时，`originalMessageId = messageId`。
- 消费失败重投时，生成新的 `messageId`，但 `originalMessageId` 保持不变。
- RabbitMQ/Kafka 适配器同时透传 `messageId`、`originalMessageId` 和 `retryCount`。
- `ConsumeContext` 同时向框架和业务暴露当前 `id`、`originalMessageId` 和 `retryCount`。
- 兼容旧消息：消息中缺少 `originalMessageId` 时，按 `originalMessageId = messageId` 处理。
- 重试不是新的业务因果消息，不应像现有 Kafka `sendWithParent` 一样每次扩展 `parentId/rootId` 链路；应保留原有链路，并单独记录消费重试次数。

消费记录表继续以 `id` 主键作为幂等约束，不调整为带 `consumerCode` 的联合幂等键。当前部署模型下，不同业务系统使用各自独立的消费记录表，同一业务系统内的一条原始消息只允许成功消费一次。

创建消费记录时，不再使用当前投递 `messageId` 作为记录主键，而是使用 `originalMessageId`：

```java
record.setId(context.getOriginalMessageId());
```

因此，首次投递和所有重试投递都会尝试写入同一个消费记录主键，数据库主键唯一性继续保证一条原始消息只被成功消费一次。`consumerCode` 继续作为审计字段，不参与幂等边界。消费记录表无需因本需求重构主键或增加新的联合唯一约束。

为防止“重试记录已落库，但原 MQ 消息 ACK/offset 提交失败”造成同一轮重试被重复创建，需为以下组合建立唯一性保护：

```text
originalMessageId + retryCount
```

该唯一性必须由数据库约束或等价的原子写入保证，不得仅依赖代码先查后写。

### 事务与 ACK 顺序

- 业务消费、消费幂等记录必须保持在同一个业务事务中；消费失败时一同回滚。
- 业务事务回滚后，使用 `REQUIRES_NEW` 保存延迟重试记录，避免被原事务回滚。
- 延迟重试记录保存成功后才可 ACK RabbitMQ 消息或提交 Kafka offset。
- 延迟重试记录保存失败时，当前 MQ 消息必须保持未确认状态。
- 重试记录重复写入命中唯一约束时，应视为该轮重试已经可靠记录，可继续确认原 MQ 消息。

### 重试继续与停止

框架不定义“重试耗尽次数”，也不内置 8 次或其他上限。每次业务消费失败后，框架将当前 `retryCount` 交给该消费者的 `ConsumeRetryPolicy`：

- 策略决定继续时，框架按策略返回的时长创建下一轮延迟重试。
- 策略可以始终返回继续，因此支持无限次重试。
- 策略决定停止时，框架不再创建重试消息。
- 策略停止时，在 `TXN_MESSAGE` 保存状态为 `DEAD`、不参与派发的终止审计记录；该记录保存成功后，才可确认原 MQ 消息。

是否有限重试、有限重试的具体次数以及无限重试时的间隔都属于消费者策略，不属于框架全局约束。

### 解析失败与业务失败

当前两种监听器都存在 context 或 payload 解析失败分支。该类消息无法安全重建业务负载，不应盲目复用“反序列化后重新发布”流程。实施时需分开处理：

- 业务消费失败：交由当前消费者的 `ConsumeRetryPolicy` 决定下一步。
- context/payload 解析失败：保留原始字节后进入独立的有限次重试或死信处理，不调用业务消费者。

本次确定不让解析失败使用消费者业务重试策略：RabbitMQ 立即 `basicNack(..., requeue=true)`，Kafka 使用原生短延迟 `nack`。这两类失败没有可靠的业务负载，不能安全创建新的事务重试消息，也不会占用线程执行长时间等待。

### 时间精度

复用现有派发线程时，到期消息的实际投递时间受 `dispatchIdleSleepMillis` 影响。默认空闲轮询间隔为 30 秒，因此实际投递可能有数十秒偏差。默认可接受“不早于策略计划时间，并在一个调度轮询周期内开始投递”的语义。

### 数据库兼容性

项目支持 MySQL、Oracle、达梦、PostgreSQL 和 SQL Server，事务消息/重试存储中的所有新字段、索引和唯一约束都需同步到五种数据库脚本。现有消费记录表的主键幂等结构保持不变。

现有自动建表器在所有表均已存在时会直接返回，不会为存量表自动增加字段或索引。因此除完整建表脚本外，必须提供明确的存量升级 SQL，不能依赖 `auto-init-schema` 完成升级。

## 验收标准

- 消费者实现可通过 `getConsumeRetryPolicy()` 独立声明重试时间表，无需全局或生产者按队列配置。
- `ConsumeRetryPolicy.fixedDelay(maxRetryCount, delay)` 可按指定次数使用相同重试间隔，达到 `maxRetryCount` 后返回停止。
- `ConsumeRetryPolicy.customDelays(delays)` 可使用任意长度且无需递增的自定义间隔，间隔数量就是总重试次数。
- `ConsumeRetryPolicy.fixedDelayForever(delay)` 可声明每次都等待 1 分钟或其他固定时长，并无限次重试。
- `ConsumeRetryPolicy.noRetry()` 与 `TransactionalMessageConsumer` 的默认实现都表示消费失败后不重试。
- `nextDelay(0)` 判定首次消费失败后的第一次重试；每完成一次重试后 `retryCount` 加一。
- 2 分钟、4 分钟、8 分钟、16 分钟、32 分钟、1 小时、2 小时、4 小时只是可验证的示例策略，不是框架默认上限。
- 固定间隔的最大重试次数和所有间隔在策略创建时完成校验，非法策略不能被创建。
- RabbitMQ 消费失败时不再通过占用消费线程长时间等待实现退避。
- Kafka 业务消费失败时不再立即创建可派发消息投递到 topic 末尾。
- 业务事务回滚后，延迟重试记录可在独立事务中成功落库。
- 只有在延迟重试或策略停止后的失败审计记录可靠落库后，才确认原 MQ 消息。
- 同一 `originalMessageId` 和同一目标 `retryCount` 在并发或重复投递下最多产生一条有效重试记录。
- 普通新消息的 `originalMessageId` 与 `messageId` 一致；重试消息使用新 `messageId`，但保持 `originalMessageId` 不变。
- 消费记录以 `originalMessageId` 作为主键落库，不调整为带 `consumerCode` 的联合幂等键，同一业务系统内一条原始消息最多成功消费一次。
- 所有重试投递保留原 `parentId/rootId` 链路，消费幂等不因当前 `messageId` 变化而失效。
- 框架不内置最大重试次数；消费者策略决定继续时必须继续调度，决定停止时不再自动投递。
- 到期重试消息不早于计划时间投递，并在一个调度轮询周期内被识别。
- RabbitMQ、Kafka 监听器测试以及五种数据库相关脚本检查通过。

## 当前进度

功能已完成。消费者可独立提供有限固定间隔、自定义间隔、无限固定间隔或不重试策略；RabbitMQ 和 Kafka 的业务失败统一通过 `TXN_MESSAGE.next_dispatch_time` 延迟派发，不再阻塞消费线程或立即重投。新消息与重试消息会透传 `originalMessageId` 和 `retryCount`，消费记录以 `originalMessageId` 作为原有单主键幂等键。

五种数据库的完整建表脚本均已增加消费重试字段及 `(original_message_id, retry_count)` 唯一键，并提供 MySQL、Oracle、达梦、PostgreSQL、SQL Server 各自的存量升级 SQL。README 已补充策略用法、消息 ID 语义和升级入口。

API、core、存储层、RabbitMQ、Kafka 的相关测试均通过。starter 代码完成编译；starter 现有全量测试仍有与本需求无关的测试夹具问题，详见风险记录。

## 风险与阻塞

- context/payload 解析失败仍使用 MQ 原生 nack/requeue；持续无法解析的毒消息需要业务侧配置死信机制处理。
- 自动建表器不会迁移存量表，上线前必须人工执行与数据库类型匹配的升级 SQL。
- 现有 30 秒空闲调度间隔会带来最多约一个轮询周期的实际投递偏差。
- 五种升级 SQL 已做静态结构测试，当前环境未连接五种真实数据库执行迁移，正式升级前仍需在对应数据库的测试实例演练并备份。
- starter 全量测试存在原有夹具失败：默认开启自动建表的用例没有提供 `DataSource`，另有 Jackson 示例对象缺少可反序列化构造方式；本次相关模块测试和 starter 编译不受影响。
