# 消费者异常重试与处理上下文

## 背景

当前事务消息消费者通过返回 `QueueMsgHandleRet` 表达事务回滚、提交前回调和提交后回调。消费者方法抛出异常时没有返回对象，监听器只能依赖外层失败处理逻辑，接口无法表达消费过程中的处理上下文。

另外，当前 `TransactionalMessageConsumer` 默认使用 `ConsumeRetryPolicy.noRetry()`。消费者发生未处理异常时，如果重试记录服务可用，可能被记录为停止重试并确认原消息，不符合“默认异常需要重新消费”的安全预期。

## 目标

- 将 `QueueMsgHandleRet` 更名为 `ConsumeHandleContext`，调整为输入型消费处理对象，并将消费者方法改为 `void` 返回值。
- 消费方法新增消费处理对象入参，使消费者抛出异常时仍可保留异常前设置的处理状态和回调。
- `TransactionalMessageConsumer` 默认使用 `ConsumeRetryPolicy.nativeNack()`，消费者未显式配置策略时，消费异常通过 MQ 原生 nack/requeue 重试。
- 保留消费者显式配置延迟重试或停止重试的能力。
- 采用 `ConsumeHandleContext` 作为消费处理对象名称。

## 范围

- 调整事务消息 API 中的消费者接口和消费处理对象。
- 调整 Kafka、RabbitMQ 消费调用器及监听器的异常处理流程。
- 调整默认消费重试策略及相关策略类型，使“延迟重试、原生 nack、停止重试”语义明确区分。
- 更新示例、README 和相关测试。

## 非目标

- 不改变正常消费成功时的事务提交、幂等和 ACK 语义。
- 不改变生产端事务消息发送和派发流程。
- 不在本需求中兼容旧的 `QueueMsgHandleRet` 消费者方法签名。

## 关键设计

### 消费者接口

消费者方法由返回处理结果改为接收处理对象：

```java
void consume(ConsumeContext context, ConsumeHandleContext handleContext, T payload);
```

监听器在调用消费者前为每条消息创建独立的默认对象。消费者即使抛出异常，监听器也可以执行该对象中已注册的 finally 回调，并读取异常发生前设置的事务处理状态。

### 默认异常重试

`TransactionalMessageConsumer#getConsumeRetryPolicy()` 默认返回：

```java
ConsumeRetryPolicy.nativeNack();
```

失败处理策略按以下语义区分：

- `nativeNack()`：不确认当前 MQ 消息，使用 Kafka nack 或 RabbitMQ requeue 进行原生重试。
- 延迟重试策略：保存下一轮重试记录，保存成功后确认当前 MQ 消息；重试记录保存失败时回退到 native nack。
- `noRetry()`：记录停止重试结果并确认当前 MQ 消息，表示消费者明确接受失败消息不再重试。

`nativeNack()` 通过独立策略类型和 `isNativeNack()` 判定与 `noRetry()` 区分；`nextDelay()` 返回空只表示该策略不创建延迟重试间隔，监听器不能仅依据空值判断最终失败动作。

### 异常处理顺序

```text
消费者抛出异常
    ↓
回滚业务事务和消费幂等记录
    ↓
执行消费处理对象中的 finally 回调
    ↓
根据 ConsumeRetryPolicy 决定延迟重试、native nack 或停止重试
```

### 命名结论

最终采用 `ConsumeHandleContext`。该名称不绑定 RabbitMQ 的 queue 术语，能够表达消费处理阶段的事务回滚、回调和控制状态，同时比 `ConsumeProcessingContext` 更简洁。

## 验收标准

- `TransactionalMessageConsumer` 默认重试策略为 `ConsumeRetryPolicy.nativeNack()`。
- 消费者抛出异常时，业务事务回滚，默认执行 MQ 原生重试。
- 消费者显式配置延迟重试策略时，延迟重试优先，成功保存后确认原消息。
- 消费者显式配置 `noRetry()` 时，失败消息被记录并确认，不再重试。
- Kafka 和 RabbitMQ 的异常、延迟重试、重试保存失败场景均有测试覆盖。
- 处理对象统一命名为 `ConsumeHandleContext`，并同步更新文档和示例。

## 风险与阻塞

- `nativeNack()` 在 RabbitMQ requeue 模式下可能导致异常消息快速循环，当前保留为默认安全重试策略，后续可结合监听容器配置、重试计数或死信策略增加保护。
- 该需求会破坏现有消费者接口，业务接入方需要同步升级实现类。
